Security audits

Every audit of Fotobogen, with its date, what it found, and what was done about each finding.

Each audit is a red team and blue team exercise: the red team attacks a running copy and reads the code looking for ways in; the blue team fixes what is found. They are carried out with an AI assistant (Claude) at the author's direction, not by an independent security firm, so read them as a careful self-examination and not as a certificate. Every finding is listed, including the ones that were not fixed.

The newest audit is open below; older ones are folded under it. To report a problem, open an issue on GitHub. If the details should not be public yet, say only that in the issue and ask for a private way to send them.

17 November 2026, two-step login (after version 1.8.0). 6 findings, none critical, high, or medium: 2 low, 4 informational. Outcome: 2 fixed, 4 accepted.

17 November 2026, the fourth audit

The fourth audit, of two-step login alone: the code after the password, the backup codes, the key a server keeps for every Fotobogen on it, the admin page, and the commands on the server. One attacker, with a running copy on this machine and the source code, sent about 60 requests of its own making. The aims: to log in without a code; to read the key or the backup codes without the password; to use one code twice; to switch two-step login on or off from another site or with an API token; and to fetch the key file by a web address. Each finding was shown against the running copy or by a test. Finding 2 was not found by the attacker: an automated review of the finished change raised it afterwards. Both fixes were made with a test that failed first.

Fixed: closed in this release. Reduced: made harder or documented, not closed. Accepted: left as it is, for the reason given. Open: not yet dealt with.

#SeverityWhat was foundOutcomeWhat was done
1LowWrong codes were limited for each address only (five in fifteen minutes). Someone who already had the password could have guessed at the six digits from many addresses at once.FixedWrong codes are also counted for the account, wherever they come from: after ten in fifteen minutes no code is looked at, right or wrong, until the wait is over.
2LowA backup file held the two-step key and the backup codes. The admin shows those only after the password is given again, but a backup is downloaded without it, so a browser left logged in was enough to fetch them. Restoring a backup could also have switched two-step login off, or brought a key of the backup's choosing.FixedThe key and codes are taken out of every backup, leaving no trace in the file. A restore leaves two-step login exactly as the site has it, whatever the backup holds. If the site's own database is too damaged to read, the restore still goes ahead, leaves two-step login off, and says so in a warning.
3InformationalThe key and the backup codes are kept readable in the site's own database file.AcceptedThe key has to be readable for a code to be checked, and the codes are kept readable so the owner can see them again. Whoever can read that file can read everything else the site holds.
4InformationalOne key serves every Fotobogen of one server account. Whoever reads one site's database, or the key file, can pass the second step of the others.AcceptedChosen so that an authenticator app holds one entry for the server. Such a reader still needs each site's password, and can already read whatever that account can. TWO_STEP_KEY_FILE gives a site a key of its own.
5InformationalThe login page says the password was right before it asks for the code.AcceptedIt has to, to ask. Guessing at the password is limited as before.
6InformationalSomeone who has the password can use up the account's ten wrong codes and keep the owner waiting, fifteen minutes at a time.AcceptedIt needs the password. The owner changes it on the server with reset-admin, which also signs everyone out.

What was tried and held: requests from another site, with no Origin header, and as plain text are refused; a browser that is already logged in cannot read the key or the codes, make new codes, or switch it off without the password; an API token and a demo visitor are refused everywhere; one code sent eight times at the same moment logs in once, an app code and a backup code alike; numbers, lists, and very long text in place of a code or a password are refused without an error; the key file is not reachable at any address tried, and is not in a backup file; nothing else the admin answers contains the key or a code; every answer is marked not to be kept by a browser or a proxy.

17 November 2026, version 1.8.0. 11 findings, none critical, high, or medium: 5 low, 6 informational. Outcome: 4 fixed, 6 accepted, 1 open.

17 November 2026, the third audit

The third audit, of everything added since version 1.7.0: the trash, pages and menu links, search, private albums, the albums offered on the front page and its shuffled order, the sample albums, and the one-line installer. One attacker, with a running copy on this machine and the source code, sent about 150 requests of its own making, raw where a browser would tidy them, and used a real browser where one was needed. The aims: to see a photo, a page, or an album a visitor may not see; to change something without being the owner; to make text typed by an owner run as script; and to learn a private album's link. Each finding was shown against the running copy or measured. The fixes were made with a test that failed first and are in version 1.8.0.

Fixed: closed in this release. Reduced: made harder or documented, not closed. Accepted: left as it is, for the reason given. Open: not yet dealt with.

#SeverityWhat was foundOutcomeWhat was done
1LowA counting script, once loaded on a public page, could come along into a private album if the visitor arrived there from that page without the server being asked. The script would then report the album's secret link to the counting service. No link on the site makes such a move by itself; it took a call to the site's own router to show it.FixedArriving at a private album from a page that carries the script now asks the server for the page afresh, and the server never puts the script there. A browser test keeps it.
2LowA photo in the trash could still be changed through the admin's API: its title, its place in the order, its tags, whether it was hidden. It is meant to be left exactly as it was.FixedChanging or moving a photo in the trash is refused; only restoring it or deleting it for good touches it.
3LowA page whose text had no spaces in it (20,000 letters, say) took about a third of a second to read, on every view. Someone with the owner's password could have made a site's pages slow.FixedAddresses are looked for only where a word begins. The longest page a site can hold is read in under a twentieth of a second, whatever it is made of; a test measures it.
4LowThe installer checked whether the folder it was given exists by following links. A link of that name leading nowhere passed the check, and git would then have written through it to wherever it pointed.FixedAnything at that name counts as there, a link that leads nowhere included. In installer 1.0.1.
5LowThe picture files of a photo in the trash, and of photos someone saw through a private album's link before the link was replaced, can still be opened by anyone who kept a picture's own address.AcceptedThe same as for a hidden photo (the first audit's finding 10). The addresses cannot be guessed. Deleting the photo for good withdraws them. The admin and the docs say so.
6InformationalA private album's link is its whole protection, and a link travels: it is in the server's log, in the browser's history, and wherever it is pasted.AcceptedIt is how a link works, and the admin says so beside the link. Make a new link ends the old one. The site sends no referrer, marks the pages never to be stored or listed, and loads no counting script on them.
7InformationalWith a counting service switched on, the service is told the address of each page viewed. For the search page that address holds the words searched for, if the service records it in full.AcceptedIt is within what choosing a counting service already means, and the docs now say it.
8InformationalA program with a manage-photos token can read a private album's link and can make an album private. One with an upload-only token can list what is in the trash, as it can the library.AcceptedA token is given only to the owner's own programs. The API guide says what each kind can reach.
9InformationalA demo visitor can read pages that are hidden, in the admin.AcceptedA demo site holds nothing private; a demo visitor is not shown private albums' links.
10InformationalThe publish script hands npm's two-factor code to npm on its command line, where another user of the same computer could see it for a moment.AcceptedThe code lasts about 30 seconds and is used at once, on the author's own machine.
11InformationalA request that carries no Origin header is told twice over that any site may read the public API. Browsers asking from another site always send that header and are told once, so nothing fails.OpenNot changed in this release.

What was attacked and held

  • The trash. A photo in the trash was looked for at seven addresses of its own and in eight lists (the grid, the feed, the sitemap, the slideshow, search, the albums, its album, its tag) and was in none. Restoring and deleting for good were refused from another site, with an upload-only token, and with no login. A photo that is not in the trash cannot be deleted for good.
  • Pages and the menu. Nineteen spellings of addresses the site uses (capitals, slashes, a circled letter, a null byte) were refused or turned into harmless ones, and the site's own twelve addresses went on answering as themselves. Twelve hostile texts in a page produced no tag and no link that could run script; ten hostile menu links were refused. Neither kind of API token could read or write pages or the menu.
  • Search. A hidden photo was not found by its title, description, or tag, and no photo by its file name or id. Nine inputs written to break out of the query found nothing and broke nothing. Forty six-word searches at once took 16 milliseconds.
  • Private albums. Fourteen public addresses were read for any trace of a private album, its name or its link: none. Eight near-misses of a real link all failed. A photo outside the album could not be reached through its link, and a photo in it gave no tags, albums, location, or download. A new link ended the old one at once. The private API carries no permission for other sites to read it.
  • The front page. Nine malformed requests for a shuffle were refused or answered plainly. Only an album the owner offers can be chosen on the front page: a hidden album, a private one, and names written to break the query all showed the ordinary page. Forty shuffles at once took 14 milliseconds.
  • The installer. A folder name cannot be read by git as an option, a version is taken only in the form of a release, and nothing typed reaches a command line on Windows.

Not tested

Browsers other than Chromium; a private album's link with the admin at an address of its own; search and shuffling on a library of many thousands of photos; the installer on Windows. Findings left open by the earlier audits are still open.

17 November 2026, version 1.7.0. 7 findings, none critical, high, or medium: 4 low, 3 informational. Outcome: 3 fixed, 1 reduced, 3 accepted, none open.

17 November 2026

This audit covered what is new since the last one, above all the slideshow for other sites (version 1.6.0), the one place where Fotobogen lets another site put one of its pages in a frame. One attacker, with a running copy on this machine and the source code, tried to get any other page into a frame, to steer the frame elsewhere, to switch the slideshow on or off without being the owner, and to make it show something a visitor may not see. It also looked at the changes in 1.7.0: full screen allowed again, and the date read from a photo. Each finding was shown against the running copy. The fixes were made with a test for each and are in version 1.7.0.

Fixed: closed in this release. Reduced: made harder or documented, not closed. Accepted: left as it is, for the reason given. Open: not yet dealt with.

#SeverityWhat was foundOutcomeWhat was done
1LowAt the slideshow's address, a wrong album or tag, a hidden album, an album named twice, and some odd spellings of the address (extra slashes, capital letters) were answered with the site's own "not found" page, menu and links included, or with the slideshow itself. That address is the one whose rules allow framing by other sites. No other site could in fact frame the result, but only because the security layer happens not to apply an address's rules to error pages, which nothing in Fotobogen guaranteed.FixedThe address is decided before any page is made. It must be spelled exactly, and an album or tag must be one a visitor may see; anything else gets a bare "not available" that cannot be framed. A hidden album answers exactly as a missing one.
2LowThe slideshow's page carried no instruction against being stored. A cache between the server and a viewer could have gone on showing it after the owner switched it off.FixedIt is marked never to be stored, so switching it off takes effect at once.
3LowOnce switched on, any site can embed the slideshow, and every viewer's browser fetches it from this server. A busy site that embeds it adds its visitors to this server's load, and there is no limit.AcceptedThe photos are public already, and a list of allowed sites was left out on purpose. Switching it off stops it everywhere at once. The admin page and the docs now say this.
4LowVersion 1.7.0 allows the site's own pages to go full screen again, which the photo and slideshow buttons need. A counting service's script on a public page could, after a click, put that page full screen and draw anything there, a false login for one.AcceptedIt is within the trust already described for a counting service, which is off unless the owner chooses one. Pages framed inside the site get no full screen, and camera, microphone, location, and screen capture stay refused.
5InformationalSwitching the slideshow off stops the framed page only. The public API stays readable from any site, as documented, so someone can still build their own slideshow of the public photos.ReducedThe admin page and the docs now say so in plain words.
6InformationalA photo whose camera data claimed a year below 100 had 1900 added to it.FixedThe date is kept as written.
7InformationalThe server's log shows which pages embed the slideshow and the addresses of the people who view it there, as for any frame.AcceptedIt is how a frame works. The docs now mention it.

What was attacked and held

  • Putting any other page in a frame. Twenty-seven spellings of addresses under /embed were tried as raw requests: dot segments, encoded dots and slashes, doubled slashes, capitals, semicolons, extra path, a null byte, a line break, a payload file. None returned anything another site can frame except the slideshow itself. The home page, the site's slideshow, a photo page, the login, and the admin kept their refusals.
  • Steering the frame. From a second site in a real browser, the frame was pointed at the home page, the login, the admin, the site's slideshow, a wrong album, and a dot-segment address: each time it showed nothing. The site's own router, told inside the frame to go to the home page, asked the server afresh and was refused. Taking that guard out made the home page appear in the frame, so a test now keeps it in.
  • Switching it on or off. Refused: a request from another site, with a "null" origin, with no origin, from a lookalike name, sent as plain text, with an API token, and with no login. A plain visit to an address changes nothing. Anything but true or false is refused.
  • What it shows. A hidden album cannot be told from one that does not exist. With the owner's login sent along, the page is the same and sets no cookie. Hostile markup in a title and alt text came out as text.
  • Counting. With a counting service switched on, the slideshow page carried no script of it and no permission to report to it.
  • The admin at its own address. The slideshow is served only at the public address; at the admin's it is sent on, and it cannot be switched from the public address. The code the admin gives points at the public site.

Not tested

Pasting the code into real site builders; browsers other than Chromium; a real proxy or CDN in front; heavy load from a busy embedding site. The seven findings left open by the audit of 16 November 2026 are still open.

16 November 2026, version 1.3.3. 36 findings, none critical: 1 high, 5 medium, 19 low, 11 informational. Outcome: 20 fixed, 3 reduced, 6 accepted, 7 open.

16 November 2026

Four separate attackers, each with its own running copy of version 1.3.3 and the source code, took one area each: login and permissions; files going in and out (uploads, backups, skins, modules); injected text and outbound requests (pages, the feed, webhooks); and the updater, the command line, and the deployment files. Each finding had to be shown working against the running copy or proven from the code. The fixes were then made, with a test for each where one could be written, and released in version 1.3.3.

Fixed: closed in this release. Reduced: made harder or documented, not closed. Accepted: left as it is, for the reason given. Open: not yet dealt with.

#SeverityWhat was foundOutcomeWhat was done
1HighA backup uploaded through the admin could carry a module. A module is code, and it ran on the server at the next start, even while listed as switched off. A stolen admin password was therefore enough to run code on the server.FixedA backup uploaded through the admin is restored without its modules, and the page says so. Modules are restored only on the server itself (the command, or a file left in the data folder), by someone who can already run code there.
2MediumA WebP file of a few kilobytes that declared a huge size was fully decoded before the size limit was applied. A handful of such uploads at once, each of them refused, took about 1 GB of memory. An upload-only token was enough.FixedThe size a WebP declares is read from its first bytes and refused before anything is decoded. Reading a picture's size is done one upload at a time.
3MediumPreviews in the photo editor were made in parallel, each decoding the whole photo. Six at once took over 600 MB. On a demo site the public demo login was enough.FixedPreviews are made one at a time; when four are waiting, the next is told to try again.
4MediumA skin whose skin.css was a link to another file had that file served to every visitor. A crafted skin folder, once installed and chosen, published the login secret.FixedSkins read only real files in their own folder, up to 2 MB. Modules refuse a linked entry file.
5MediumThe database, the copies made before updates, backups written by the command line, and .env could be read by any other user of the same machine. The database holds the password in scrambled form, API token hashes, and webhook secrets.FixedThe database, its copies, backups, the update record, and a new .env are readable by their owner only; the folder of uploaded photos likewise. An .env that already exists keeps the permissions it has: run chmod 600 .env.
6MediumAn update runs code fetched from the repository the copy was cloned from, without checking a signature. Whoever controls that repository, or changes where "origin" points, can run code on the server at the next update.OpenNot changed. What limits it: only the logged-in owner can start an update; the version comes from Fotobogen, never from the request; a tag must descend from the installed version; a tag that was moved is refused. Signed release tags, checked before the switch, are planned.
7LowThe check that a change comes from the site's own pages compared the name but not the scheme, so a page loaded over http could change a site reached over https. Browsers that treat http and https as different sites already block this.FixedOnly http and https origins are accepted, and https is required when the request is known to have come over https.
8LowThe admin, its API, setup, and login are guarded by their paths. Percent-encoded spellings (/api/%61dmin/…) reached the same handlers without passing the first guard. Nothing was exposed, because every handler checks the login itself.FixedEncoded spellings of those paths are refused before anything else looks at the request.
9LowA login never expired while it was in use, so a copied cookie could be kept alive for ever.FixedA login ends 90 days after it was made, however much it is used.
10LowHiding a photo takes it off the site, but its picture files can still be fetched by anyone who has their addresses.AcceptedDocumented. The addresses cannot be guessed; deleting the photo, or rendering it again, withdraws them. Giving a hidden photo new addresses is planned.
11LowWith no site address set, the feed, sitemap, and page links were written with whatever Host header the request carried.ReducedA Host header that is not a name or address is refused. Setting the site's address (Search and sharing, or SITE_URL) fixes the links entirely, and the docs say to. A valid but wrong Host passed on by a misconfigured proxy is still echoed when no address is set.
12LowControl characters in a photo's title or description made the feed unreadable for every reader. A manage-photos token was enough.FixedCharacters XML does not allow are left out of the feed and sitemap.
13LowPages believed the X-Forwarded-Proto header without TRUST_PROXY, so a visitor could flip http and https in a page's own canonical link.OpenNot changed. It affects only the response to the visitor who sent the header, and not at all once the site's address is set.
14LowOne range of IPv6 addresses that carry an IPv4 address inside them was missing from the list of private addresses a webhook may not call.FixedThe range is refused.
15LowWith no web server in front, an upload over the limit was refused only after all of it had been read, using memory meanwhile. A login or token was needed.AcceptedThe web servers Fotobogen is documented with cut such an upload off themselves.
16LowRestoring a backup has no size limits: a small zip can unpack to fill the disk. Admin only.OpenNot changed in this release.
17LowThe documentation said a backup file "does not open your site". It holds the scrambled password, token hashes, and every photo; and a restored backup brings its own login and API tokens.FixedThe admin, README, and docs now say what a backup holds and to restore only your own. A restore ends every earlier login.
18LowTwo updates started at once from the command line both ran, building in the same folder.OpenNot changed. The admin's button was tested and starts only one.
19LowThe record of running copies believed any process number written in it, so "stop the running copy" could stop an unrelated process.ReducedProcess numbers below 2 and processes belonging to other users are ignored. A leftover record whose number has been reused by another of your own processes can still be mistaken for a copy.
20LowA version written as 1.4.00 or v1.4.0 on the command line was fetched and then rolled back with a full rebuild.FixedThe version is put in one spelling first.
21LowThe nginx examples did not send the header that keeps browsers on https (HSTS); only the Caddy file did.FixedAdded to every nginx example.
22LowPublishing an old release's Docker image again by hand moved the "latest" tag back to it.Fixed"latest" moves only to the newest release.
23LowThe build actions are pinned by version tag, not by commit, and Docker images are not signed.OpenNot changed in this release.
24Lowpnpm fotobogen backup wrote through a link to another file, and the file could be read by other users.FixedA link is refused, and the backup is readable by its owner only.
25LowTwo advisories in packages used to build the site (minimatch, esbuild), neither in code that answers visitors.OpenWaiting for the packages that bring them in to update.
26InformationalA request carrying anything shaped like an API token skipped the same-site check on every address, not only the admin API where tokens work.FixedThe token stands in for the check only on the admin API.
27InformationalAnswers from the admin and the login carried no instruction against being stored by a browser or proxy.FixedThey are marked never to be stored.
28InformationalA TRACE request, or a Host header that could not be read, produced an error and a long entry in the log.FixedRefused at once, quietly.
29InformationalThe link to a release's notes was checked by how it began, so an address with "../" in it could lead to another project on GitHub. It needed a forged answer from GitHub.FixedThe address is parsed and must resolve inside the project.
30InformationalSite text placeholders such as {constructor} were filled from built-in names. Owner only, and harmless.FixedOnly the names a text is given are filled in.
31InformationalA webhook message can be sent again by someone who captured it: the signature says who wrote it, not when.ReducedThe time sent is inside the signed message; the docs now tell receivers to refuse old ones and to use https.
32Informational/api/health tells anyone the exact version.AcceptedMonitoring uses it, and the software is open source.
33InformationalA demo visitor sees hidden photos in the library, and an upload-only token can list the library, location included.AcceptedA demo site holds sample photos; a token is given only to your own programs.
34InformationalThe date a photo was taken is shown whether or not "show camera details" is on.OpenNot changed in this release.
35InformationalAn API token has no limit on how much it may upload.AcceptedA token is given only to your own programs, and can be revoked.
36Informationalfotobogen.com, the project's own website, loads its visit counter from Plausible without a content security policy.AcceptedIt is a static page with no login. Installed sites load nothing from elsewhere.

What was attacked and held

  • Login and permissions. No way was found to act as the owner, to make an API token do more than its kind allows, or to make a demo visitor change or read what it should not. Setup cannot be run twice. The limit on wrong passwords held against parallel guesses and forged addresses. Nothing told a real username from a wrong one. Every admin address checks the login itself.
  • Changes from another site. Requests with no origin, a "null" origin, another port, or a lookalike name were all refused. No address changes anything on a plain visit.
  • Text on pages. Hostile markup in titles, descriptions, tags, album names, file names, camera details, and every settings field never ran as script, in a real browser, on 8 public and 12 admin pages. The site's content policy refused injected scripts and links.
  • Database. Every query binds its values; no way was found to inject SQL.
  • Uploads. Files that are not photos, SVG, disguised files, and oversized images were refused. File names cannot reach the disk. Nothing from the camera survives in the copies visitors see.
  • Reading files. No path was found to read a file outside the resized copies, by any encoding. Addresses of a photo hidden from the start cannot be guessed.
  • Restore. Entries with "../", absolute paths, and links inside a backup were refused or written as plain files; the login secret cannot be replaced.
  • Webhooks. Every spelling of this machine or a private network that was tried was refused, both when saved and again when called, so a name cannot be switched between the two. Redirects are not followed.
  • Updates. Nothing in a request, a GitHub answer, or a tag name reached a command line. A demo visitor or a token cannot start an update. Forty simultaneous presses started exactly one.
  • Settings file. Answers to the first-start questions cannot add lines to .env.
  • Docker. The image runs as an ordinary user and holds no .env, no git history, and no data.

Not tested

A real nginx, Caddy, or Docker (their files were read, not run); Windows; browsers other than Chromium; attacks from the network such as flooding; and the 90-day login limit, which has no automated test.
