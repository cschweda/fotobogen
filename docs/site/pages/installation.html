What the machine needs

Fotobogen checks the machine every time it starts and refuses to run on one that cannot run it properly, saying what to fix. The figures below are what that check enforces.

MinimumRecommended
Processor1 virtual CPU, x64 or arm642 virtual CPUs
Memory1 GB, with 2 GB of swap2 GB or more
Disk10 GB25 GB or more, SSD, sized to your photographs
SystemUbuntu or Debian (a current LTS release), macOS, or Windows
SoftwareNode.js 24 with pnpm 10, or Docker with Compose
  • Memory. Fotobogen will not start with less than 900 MB available to it, and warns below 2 GB when there is no swap. It resizes one photo at a time to stay small: a 40-megapixel photo was processed inside a container limited to 1 GB, using about 250 MB at its peak.
  • Building needs more than running. Installing from source takes more memory than the running site. On a 1 GB server add swap first (the commands are below). A 2 GB server needs none, and neither does a Docker install, which downloads an image that is already built.
  • Disk. It will not start with less than 500 MB free and warns below 2 GB. Most of the space goes to your photographs as uploaded; the resized copies are smaller. A backup zip is about the size of your originals, so leave room for one.
  • Other Linux distributions may well work but are reported as untested.

What has and has not been tested. Every change is installed, built, and tested on Ubuntu and on Windows, and a 1 GB memory limit was tested in Docker. A real 1 GB rented server, and Docker on Windows, have not been tried yet. If you can afford it, rent the 2 GB size.

macOS

For trying Fotobogen, or running it on a Mac at home. Works on Apple silicon and Intel.

  1. Install Node.js 24. Download the installer from nodejs.org, or, if you use nvm, run nvm install 24. Check with node --version; it should print v24 and some more.
  2. Install pnpm, which fetches Fotobogen's parts: 
    npm install -g pnpm@10
  3. Get Fotobogen and build it. In Terminal: 
    git clone https://github.com/cschweda/fotobogen.git
cd fotobogen
pnpm install
pnpm build
pnpm start
    If git is missing, macOS offers to install it the first time you type the command.
  4. pnpm start checks the machine, then prints the address and a setup token: 
    Fotobogen setup token: 3b213e46bd70894ad18f1357791b1f18
Open the site in a browser and enter this token to finish setup.
Fotobogen is running. Open it in a browser on this computer:

    http://localhost:5150

Logging in works at that address, or over https.

If pnpm install stops and says Node.js is too old, the terminal you are in is using an older version, even if a newer one is installed. With nvm, nvm use 24 switches the terminal you are in; nvm alias default 24 only affects terminals opened afterwards. nvm keeps tools separately for each version of Node.js, so install pnpm again after switching: npm install -g pnpm@10.

To keep it beside a copy of the source, give the folder another name when you clone: git clone https://github.com/cschweda/fotobogen.git fotobogen-live. Each folder is its own site with its own data.

Leave that Terminal window open while you use the site; Control + C stops it, and pnpm start starts it again with everything as you left it. Go on to the first run.

To reach it from another device on your home network, use the Mac's name or address in place of localhost, for example http://my-mac.local:5150. You can look around the public site that way, but logging in works only over HTTPS or on localhost, so do the admin work on the Mac itself. From another computer you can borrow the Mac's localhost over SSH: run ssh -L 5150:localhost:5150 you@my-mac.local there, leave it open, and browse to http://localhost:5150.

Windows

Windows 10 or 11. No compiler or Visual Studio is needed.

  1. Install Node.js 24 from nodejs.org, and Git from git-scm.com.
  2. Open PowerShell and install pnpm: 
    npm install -g pnpm@10
  3. Get Fotobogen and build it: 
    git clone https://github.com/cschweda/fotobogen.git
cd fotobogen
pnpm install
pnpm build
pnpm start
  4. It prints the address, http://localhost:5150, and the setup token. Go on to the first run.

If PowerShell refuses to run pnpm because scripts are disabled, run Set-ExecutionPolicy -Scope CurrentUser RemoteSigned once and try again.

One difference from macOS and Linux: Windows has no equivalent of the file permission Fotobogen uses to keep its secret key private to your user, so that file has the same permissions as the folder it is in. Keep the data folder somewhere only you can read.

Docker on a fresh VPS

For a newly rented server running Ubuntu, with nothing else on it. Fotobogen runs behind Caddy, which gets an HTTPS certificate for your domain by itself and renews it.

Before you start

  • A server of the size above, and a way to log in to it with SSH.
  • A domain name, with an A record pointing at the server's address. Set this first: Caddy cannot get a certificate until it has taken effect.
  • Ports 80 and 443 open in the server's firewall.

Steps

  1. Install Docker, using Docker's own script, and let your user run it: 
    curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
    Log out and in again so the second line takes effect.
  2. On a 1 GB server, add swap (skip this with 2 GB or more): 
    sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
  3. Get Fotobogen: 
    git clone https://github.com/cschweda/fotobogen.git
cd fotobogen
mkdir -p data
cp .env.sample .env
    mkdir -p data matters: it makes the data folder belong to you instead of to root.
  4. Edit .env (nano .env) and set your domain by removing the # from this line and changing the name: 
    DOMAIN=photos.example.com
    If id -u prints something other than 1000, also set PUID and PGID to what id -u and id -g print.
  5. Start it: 
    docker compose up -d
    This downloads the published image (ghcr.io/cschweda/fotobogen) and Caddy, and starts both. Nothing is built on your server.
  6. Read the setup token: 
    docker compose logs app

Open https://photos.example.com (your own domain) and go on to the first run.

Docker starts Fotobogen again by itself after a reboot. To update later: docker compose pull, then docker compose up -d.

To build the image yourself instead of downloading it, remove the # from # build: . in docker-compose.yml and add --build to the command. On a 1 GB server that needs the swap from step 2.

Docker on a Laravel Forge server

For a server that Laravel Forge set up. There, nginx already answers on ports 80 and 443 and Forge manages the certificate, so Fotobogen runs alone in Docker, listening only on the server itself, and Forge's nginx passes visitors to it.

  1. Install Docker on the server and let the forge user run it. Log in as forge with SSH: 
    curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker forge
    Log out and in again. On a 1 GB server, add swap too.
  2. Create the site in Forge with your domain, and install the repository cschweda/fotobogen into it (branch main). If Forge offers to install Composer dependencies, decline; there are none.
  3. Start Fotobogen. In the site's folder (/home/forge/photos.example.com): 
    mkdir -p data
PUID=$(id -u) PGID=$(id -g) docker compose -f docker-compose.forge.yml up -d
    This downloads the published image; nothing is built on your server.
  4. Point nginx at it. In Forge, open the site's nginx configuration and paste in the blocks from deploy/forge-nginx.conf, changing the two marked paths to your site's folder.
  5. Issue the certificate in Forge (Let's Encrypt).
  6. Read the setup token: 
    docker compose -f docker-compose.forge.yml logs app

Fotobogen listens on 127.0.0.1:5150 only. If something else on the server uses that port, set PORT in a .env file in the site's folder and use the same number in the nginx configuration.

The deploy script. Paste deploy/forge-deploy.sh into Forge's Deploy Script box. Forge's Deploy button then downloads the newest published image and restarts Fotobogen with it.

Linux without Docker

For Ubuntu or Debian, running Fotobogen directly with Node.js, kept alive by pm2, behind nginx.

  1. Install Node.js 24. The simplest way is nvm: install it as its page describes, then 
    nvm install 24
npm install -g pnpm@10 pm2
  2. On a 1 GB server, add swap before building.
  3. Get, build, and start: 
    git clone https://github.com/cschweda/fotobogen.git
cd fotobogen
pnpm install --frozen-lockfile
pnpm build
pnpm fotobogen init
pm2 start ecosystem.config.cjs
pm2 logs fotobogen
    pnpm fotobogen init is optional: it asks for the port, the site's address, and demo mode, and writes .env. There is nothing to edit in ecosystem.config.cjs, which takes the port from .env. The last command shows the setup token.
  4. Start it at boot: run pm2 save, then pm2 startup, and run the line that prints.
  5. Put nginx in front of it, as in the next section.

To update: scripts/rebuild.sh, which pulls the new code, builds it, and reloads.

nginx in front of the app

Without Docker, Fotobogen listens on 127.0.0.1:5150, which only the server itself can reach. nginx answers the public and passes each request on. Save this as /etc/nginx/sites-available/photos.example.com, with your own domain:

server {
    listen 80;
    listen [::]:80;
    server_name photos.example.com;

    # The largest upload nginx lets through. Keep it equal to MAX_UPLOAD_MB.
    client_max_body_size 50m;

    location / {
        # Where Fotobogen is listening.
        proxy_pass http://127.0.0.1:5150;
        proxy_http_version 1.1;
        # The name the visitor asked for. Without this, saving in the admin is refused.
        proxy_set_header Host $http_host;
        # The visitor's own address, for the limit on wrong passwords.
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        # Whether the visitor used http or https.
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 120s;
    }
}

Switch it on, check it, reload, and add a certificate with Certbot:

sudo ln -s /etc/nginx/sites-available/photos.example.com /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx
sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d photos.example.com

Visitors must reach the site over HTTPS, or logging in will not work.

What you seeCause
502 Bad GatewayFotobogen is not running, or is on another port. Run pm2 status and pm2 logs fotobogen.
Saving in the admin says "This request did not come from this site"The proxy_set_header Host $http_host; line is missing.
413 Request Entity Too Large on uploadclient_max_body_size is smaller than the file. Raise it and MAX_UPLOAD_MB together.
Logging in returns to the login pageThe site is being used over http.

Laravel Forge with pm2, no Docker

Fotobogen runs under pm2 as the forge user, and the nginx that Forge manages passes requests to it. This follows Forge's usual way of working but has not been tried on a Forge server yet.

  1. Create the site in Forge with your domain, as a project type with no PHP, and install the repository cschweda/fotobogen (branch main) into it.
  2. Install Node.js 24, pnpm, and pm2 for the forge user, over SSH: 
    curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/master/install.sh | bash
source ~/.nvm/nvm.sh && nvm install 24 && nvm alias default 24
npm install -g pnpm@10 pm2
    On a 1 GB server, add swap first.
  3. Build and start in the site's folder: 
    cd /home/forge/photos.example.com
pnpm install --frozen-lockfile
pnpm build
pnpm fotobogen init
pm2 start ecosystem.config.cjs
pm2 logs fotobogen
    pnpm fotobogen init asks for the port, the site's address (https://photos.example.com), and demo mode, and writes .env; the pm2 file takes the port from there. The last command shows the setup token.
  4. Make it start after a reboot: pm2 save, then pm2 startup, and run the sudo command it prints.
  5. Point nginx at it. In Forge, open the site's nginx configuration. Inside the server block, replace the location / block with the blocks from deploy/forge-nginx.conf, changing the two marked lines. Leave the rest of what Forge wrote as it is.
  6. Issue the certificate in Forge.
  7. Set the deploy script, so that Forge's Deploy button updates the site: 
    cd /home/forge/photos.example.com
source ~/.nvm/nvm.sh
git pull origin $FORGE_SITE_BRANCH
pnpm install --frozen-lockfile
pnpm build
pm2 reload ecosystem.config.cjs --update-env
    The source line matters: Forge runs the script without your login shell's setup, so Node.js would not be found without it.

An existing droplet with nginx: what to change

For a DigitalOcean droplet, or any server, that already runs nginx and other sites, managed by Laravel Forge or by hand. Fotobogen does not replace nginx or touch your other sites. It runs as one more program on a port of its own, reachable only from the server itself, and one site's nginx file is changed to pass requests to it.

Part of the serverWhat changes
nginx itself, its main file, your other sitesNothing
The firewallNothing. Fotobogen listens on 127.0.0.1, so its port is not opened to the internet.
The certificateIssued the usual way: Forge's SSL tab, or Certbot
One site's nginx fileThe six changes below

The changes go in that site's server { ... } block. On Forge: the site, Edit Files, Edit Nginx Configuration. By hand: /etc/nginx/sites-available/photos.example.com.

ChangeWhy
1. Add client_max_body_size 50m;nginx's own limit is 1 MB, which refuses nearly every photo with 413. Keep it equal to MAX_UPLOAD_MB (50 unless you changed it). Set here, it applies to this site only and wins over any server-wide value.
2. Replace the location / { ... } block with one that has proxy_pass http://127.0.0.1:5150;This is the pointer to the app. Use the port Fotobogen runs on: PORT in its .env, or 5150 if that is not set. A second Fotobogen site on the same droplet needs a different one.
3. In that block: proxy_set_header Host $http_host;Without it, saving anything in the admin answers "This request did not come from this site".
4. In that block: proxy_set_header X-Forwarded-Proto $scheme; and proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;So Fotobogen knows the visitor used https, and counts wrong passwords by visitor and not all against nginx.
5. In that block: proxy_http_version 1.1; and proxy_read_timeout 120s;A large upload takes longer to arrive and be checked than nginx's 60 seconds.
6. Remove the location ~ \.php$ { ... } block, if the site has oneFotobogen has no PHP. Harmless if left, but nothing uses it.

Leave everything else as it is: the listen lines, server_name, the certificate lines, and on Forge every include forge-conf/... line. The root line can stay; it is no longer used.

Changes 1 to 5, ready to paste:

client_max_body_size 50m;

location / {
    proxy_pass http://127.0.0.1:5150;
    proxy_http_version 1.1;
    proxy_set_header Host $http_host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 120s;
}

deploy/forge-nginx.conf is the same with one addition: nginx serves the resized photos from disk itself. Forge checks the file and reloads nginx when you save. By hand: sudo nginx -t, then sudo systemctl reload nginx.

On the app's side

Two settings go with the proxy. Both are already set in ecosystem.config.cjs and the Docker compose files.

  • HOST=127.0.0.1, so only nginx can reach the app.
  • TRUST_PROXY=1, so the app believes the headers in change 4. Set it only when the app really is reachable through nginx alone.

Also set the site's address, as SITE_URL=https://photos.example.com in .env or under Search and sharing in the admin, so links to your photos begin with your domain.

Room on the droplet. Running, Fotobogen used about 130 MB of memory when measured idle, and uses more while it resizes photos (the pm2 file restarts it at 600 MB). Building it (an install or update without Docker) needs about 2 GB counting swap, for a few minutes; on a small droplet, add swap first, or use the Docker image, which is already built.

Questions at the first start

The very first time you run pnpm start in a terminal, after the machine has been checked, Fotobogen asks three things the server has to know before it starts. Press Enter to accept what is suggested.

QuestionEnter meansWhat it sets
Port to run on?5150, or the next free port above itPORT. A port you type is used exactly; one that is in use is refused, and you are asked again.
Site address?Not setSITE_URL, your site's address if it has a domain name. It can also be set in the admin.
Switch demo mode on?NoDEMO_MODE. Only for a site meant to show Fotobogen off.

The answers are saved to .env in Fotobogen's folder, and it does not ask again. To change them, edit that file, or run pnpm fotobogen init to be asked again; your other settings in .env are kept. Then restart.

On a server, the first start is usually under pm2, where nothing is asked. Run pnpm fotobogen init there before pm2 start to answer the same questions.

Nothing is asked when nobody is at the keyboard: under pm2, in Docker, on Laravel Forge, or from a script. Nor when .env already exists, or PORT, SITE_URL, or DEMO_MODE is already set. A server never waits for an answer. To switch the questions off in a terminal too, set FOTOBOGEN_NO_QUESTIONS=1.

Whether to start with sample photos is asked in the browser, next.

In a terminal, the machine check and these questions are in colour: green for what is good, yellow for a warning, red for what stops the start. The words ok, WARN, and FAIL are always printed too. Colour is left out of log files, and NO_COLOR=1 switches it off.

The first run

However you installed it, you now have an address and a setup token: 32 letters and digits that Fotobogen printed when it started. The token proves that the person setting up the site is the person who can see the server.

  1. Open the address in a browser. A six-step wizard opens.
  2. Enter the token.
  3. Name your site, and give it a tagline if you like.
  4. Create the admin account: a username, and a password of at least 12 characters.
  5. Choose the grid (photos keeping their shape, or equal squares) and whether a photo opens over the grid or on its own page. Both can be changed later.
  6. Choose to start empty, or to download 25 sample photographs so there is something to look at. You can add or remove the samples later.

The wizard then closes for good and you are logged in. The first page you see asks you to confirm that backups are your responsibility. After that: using Fotobogen.

The token is printed at every start until setup is finished, and is also in the file data/setup-token. If you lose it, restart Fotobogen or read that file.

Settings on the server

Nothing has to be configured. Settings for one machine live in .env in Fotobogen's folder: the questions at the first start write it, or copy .env.sample to .env yourself. Edit it and restart. Docker reads the same file.

SettingDefaultWhat it does
PORT5150The port. Left unset, a busy 5150 moves up to the next free port. Set, it is used exactly, and Fotobogen stops if it is taken.
DATA_DIR./dataWhere the site keeps everything.
SITE_URLnoneYour site's proper address, such as https://photos.example.com. Used wherever a full address is written out: a photo's links in the admin, the feed, the sitemap, and what search engines are told. Without it, links made on your own machine begin with http://localhost:5150. It can also be set in the admin, under Search and sharing.
DOMAINnoneDocker quick start only: the domain Caddy gets a certificate for.
PUID, PGID1000Docker only: the user and group that own the files in data.
MAX_UPLOAD_MB50The largest file that can be uploaded. If you raise it, raise the limit in Caddy or nginx as well.
MAX_MEGAPIXELS100The largest image, as width times height.

Every other value is listed and explained on the configuration page.

Two copies on one machine. If Fotobogen is already running when you start it in a terminal, it asks whether to run both (the new one gets its own port), stop the running one, or cancel. Two copies never share a data folder.

Watching that it is up

The address /api/health needs no login and answers 200 when the site and its database are working, and 503 when they are not. Point UptimeRobot or a similar monitor at https://your-site.example/api/health.

Updating

Updating an installation you already run has a page of its own: how you hear that a new version is out, updating from the admin, updating by hand, and going back. In short: a copy installed with git updates from Admin, System; Docker updates with docker compose pull, then docker compose up -d.
